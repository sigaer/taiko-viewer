# 年度报告验收续轮：解除环境阻塞，跑通真实业务链路

## 本轮目标与依据

依据用户提供的《年度报告发布验收 — 2026-09-29》和《有界年度验收探测》。上一轮记录的候选为 0.75.8 / 8160538；开始前仍需读取当前工作区，不能假定 HEAD 未变化。

本轮不是重做测试平台，也不是放宽生产保护。目标依次是：固定候选产物 → 准备最小可写隔离环境 → 完成实际鉴权、生成和服务端分享 → 有界并发与混合负载 → 报告可验证的发布边界。

30 个冷身份是后续完整冷样本专项的配置，不应成为第一次单事务冒烟的前置条件。新增小样本 smoke 模式时保留原有完整模式及其约束，不能把小样本结果冒充 30 身份验收。

保持“不默认部署、不重启生产、不扩大入口”的约束。本指令不批准上线，也不授权操作真实用户数据、生产缓存或生产服务配置。

## 1. 固定候选产物，解决证据与提交不一致

读取适用的 AGENTS.md、版本规范及部署规范，保留所有已有未提交修改，不 reset、不清理工作区，也不擅自提交用户原有文件。

上一轮报告说明：构建使用基线 archive 加本轮覆盖文件，包含未提交的 assets/data/title_song_relations.json 以及当前 public 资源。因此，不能只凭 8160538 或版本号断言构建等于纯提交产物。

本轮优先在独立快照中使用明确的候选提交构建；不把原工作区的未提交文件自动混入。若需要沿用上一轮完整快照，必须明确列出额外输入，并标记该结果不能直接代表纯 Git 提交的发布。不要擅自决定这些额外修改应发布或应丢弃。

记录：commit、dirty/额外输入清单及哈希、应用版本、算法版本、依赖锁文件哈希、关键资源/称号关联文件哈希、build ID、产物 manifest、运行配置摘要和 worker 版本。凭据不得进入记录。

所有后续业务与浏览器结果必须能关联到实际候选产物。若因修复产生新候选，复测对应链路并更新清单；不要把旧构建结果直接标为新构建通过。

## 2. 把“缺环境”落实为具体可完成事项

报告已记录 taiko_annual_poster_test 的 SELECT DATABASE / CURRENT_USER / SHOW GRANTS 只读核验通过。这不是可写隔离环境已经完成的证明，但也不能再笼统写“没有测试库”。

先核实这次运行所需的实际依赖。在已有授权和权限范围内，完成：

- 测试数据库、受限账号、必要表结构，以及本轮唯一 runId 的合成记录。检查实际库名、权限、所有权和现有使用情况；不得 DROP 数据库或清空他人测试记录。准备与清理仅针对本轮自己创建的记录。
- 独立 userdata、summary/cache、admission、分享输出、临时目录和测试会话/签名配置。核实 realpath 与实际写入位置，不读取或覆盖生产私有数据。
- 候选 Nuxt 服务及实际 Python/Chromium worker 的启动参数、环境、队列、缓存路径和 cgroup。尤其检查经 systemd 另行启动的 worker，不能以主进程环境或 RSS 代替 worker 隔离证明。
- 网络与副作用边界。禁止邮件、社区同步、生产队列和第三方写入；本地受控静态素材可以用于隔离业务测试，但要在报告中说明这不验证真实 CDN/装扮可用性。未使用的对象存储或外部队列，凭代码及运行证据记为 NOT_APPLICABLE，不为了填表新建依赖。
- 继续使用现有 QA 资源限制，保留共机生产健康与共享数据库监测。低负载也不等于没有共机影响。无法核实关键写入、外发或 worker 边界时，不启动相应业务测试。

已有环境变量和 isolationEvidence 不能代替核实结果，不得通过补几个 true 值绕过保护。

实现最小 fixture/bootstrap 入口，复用现有测试设施，不另建大型框架。该入口默认拒绝、显式 opt-in，核实测试库后才准备本轮记录；秘密保存于仓库外 0600 文件，不打印 cookie。

若确实缺权限，只报告具体缺失项、已验证事实、需要操作者执行的最小动作；继续完成其他独立项。不要再用笼统的“尚无完整环境”替代定位。

## 3. 先跑少量合成账号的真实业务闭环

这里明确调整执行顺序，而不是取消真实样本要求：先用受控合成账号经过真实数据库、登录/会话、访问资格、接口、Python generator 和服务端 renderer；授权真实用户的代表性与真机验证仍单独列项。

第一批仅准备：普通有效、稀疏但有效、高历史事件量三个账号，以及一个预期 INSUFFICIENT_DATA 的账号。并发场景需要的新冷身份后续按需追加。

高历史事件量样本必须包含实际快照/事件记录，不再只把 UI 的演奏次数改成 999999。样本须满足当前算法窗口和输入格式，记录数量、覆盖范围及独立可核对的关键预期；不改变算法或年度区间来迁就样本。

先用一个普通账号走单事务，验证脚本与响应字段，再扩展其他账号。通过实际候选 Nuxt 服务依次完成：

1. 真实登录或项目既有会话流程 → auth/me → 年度访问资格。
2. summary envelope → 正常 build POST → 有界 job 轮询 → completed → 最终 summary。失败、超时、轮询中断不能记为成功。
3. 从实际入口进入浏览器，浏览当前有效页面直到 final/poster，不通过 fixture 注入、started=true 或 mock summary 替代业务链路。
4. 浏览器实际点击保存，触发真实 share-card POST，保持 syncCommunity:false；下载实际 imageUrl，完整 PNG 解码，核对用户、语言、尺寸及关键内容。
5. 重复读取与重复分享，核对命中/复用及最终产物。至少覆盖两个有效身份和 zh/ja；不能只检查 HTTP 200 或磁盘已有图片。
6. 用不同账号尝试读取另一个账号的受保护 summary/job/share image，按真实接口契约验证拒绝和不泄露。记录不应包含完整私有数据或秘密。
7. 数据不足账号进入正确终态，多次刷新不产生无限生成；不要要求它完成本来不应出现的海报流程。

正常路径不自动重试掩盖首次失败。修复后重跑属于独立测试记录。

这部分通过只能称“隔离环境合成账号真实业务链路通过”，不能称“真实用户数据覆盖、生产分享或线上资源已验证”。

## 4. 单独归因 8 次预渲染数据库鉴权拒绝

先读取完整构建日志和调用来源，不预设为生产故障，也不因 build.exit=0 忽略。

对每类错误回答：哪些页面/插件在构建阶段调用 auth/me，匿名预渲染是否需要数据库，受影响的 HTML/payload 是否正确，候选产物运行后的匿名和已登录行为是否正常。

按实际架构做最小处理：无需会话的公开预渲染避免不必要的构建期会话访问；确需数据库的构建步骤只使用明确受限的测试依赖。不得注入生产凭据消除日志、绕过正式鉴权、把所有数据库异常吞成匿名，也不默认关闭全部预渲染。

重验受影响公开页面及实际运行态的匿名/登录入口，给出 LIMITED 保留或解除的证据。若修改公共鉴权逻辑，增加对应回归，不只重跑年度组件。

## 5. 有界并发：补上不同用户同时首次生成

保留原有负载脚本。第一条正向事务通过后，再逐项执行；脚本不因“压力测试”获得任何生产写入权限。

### 5.1 同用户去重

same2 和 same5 分别用全新身份与输入 revision；记录请求、job、admission 和实际 Python 计算调用的对应关系。正常成功冷路径应证明实际只执行一次所需计算，不能只凭多个请求返回相同 summary 判定去重通过。

### 5.2 不同用户冷并发

新增独立场景：两个不同冷账号同时首次生成。健康通过后，用三个不同的新冷账号检验现有活跃上限和排队行为。每组身份不得已被前序冒烟预热。

报告中的“30 个用户串行冷生成”测的是串行冷路径；same2/same5 测的是同一计算键去重。二者均不能替代本场景。

记录各账号排队时间、计算时间、总完成时间、实际运行进程数、失败/拒绝/超时及压力结束后的恢复。不要修改 generator 并发配置来让测试通过。

### 5.3 分享与混合负载

对两个不同的已有 summary 触发未命中的真实分享，并发量从 2 个开始；观察 renderer 串行/排队及最终 PNG。与同一 fingerprint 的缓存命中、重复点击分开统计。

随后在已验证的低强度热读取中，叠加一次冷生成和一次未命中分享，观察读接口是否受影响，以及 generator/renderer 的真实资源占用。混合场景必须有更保守的总并发/资源保护，不同时叠加高档热流量。

这些场景都只证明对应的有限请求组，不声称恒定到达率或总体容量。

## 6. 分档探测与停止条件

最小闭环和监控确认后，按原配置先执行 warm 1/s × 120s，再低档恢复观察。该阶段不等待发布流量目标，但目标未知必须记录为 TARGET_LOAD_UNSPECIFIED。

只有上一档同构建/同环境结果健康、无时隙丢弃且队列/资源恢复，才进入 3/s、5/s；10/s 短突发保持原前置条件。不要把 warm 吞吐量解释为新用户冷生成吞吐量。

原 30 身份冷样本专项继续保留，等 fixture 入口可用后执行。小样本预检不能替代它；串行 30 身份完成也不能代替冷并发容量。

各档分别运行，不把整套矩阵强塞进 15 分钟硬截止。测试服务、worker 和负载监督各自生命周期必须明确，均保留资源约束；不能为维持服务跨档运行而逃出 cgroup 限制。启动、退出、超时和未完成任务均须有记录。

报告至少保留 started/completed/failed/unfinished、HTTP 数量、droppedSlots、实际窗口、成功延迟分位数、失败耗时、队列/admission、主服务与独立 worker/共享数据库的可获得资源证据，以及降压后恢复情况。

已有脚本门槛及资源保护不得偷偷放宽。所有延迟目标和超时上限均为测试配置，非实测 SLA。没有足够样本时仍可记录分位数，但须显示样本数，不能宣称精确容量。

服务端观测丢失、身份/版本不符、内存或队列危险、共机生产健康恶化时停止本轮负载。不要杀生产进程，也不要为了“清理”删除正在使用的文件或任务。
