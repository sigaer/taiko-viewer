# 太鼓年度总结 Scene-based UI 设计总纲

## 1. 文档定位

本文档是年度总结表现层的最高级设计约束。它承接《太鼓年度总结_第二阶段复盘与SceneBasedUI大改主控方案》，用于约束后续组件、页面、动效和验收，不修改 summary v4、后端统计、缓存、路由或 23 页业务顺序。

年度总结的产品类型是：

> 以玩家、歌曲和鼓点数据为素材的移动端年度回顾演出 H5。

它不是 dashboard、SaaS landing page、数据报告、卡片集合或长图表页面。视觉参考应来自节奏游戏赛季结算、祭典舞台和音乐年度回顾，而不是后台管理系统。

## 2. 体验目标

用户完成浏览后应记住三件事：

1. 这是属于自己的太鼓年度舞台。
2. 每一页都有一个清晰、可复述的记忆点。
3. 数据不是被陈列出来，而是在合适的时刻被揭示出来。

体验关键词：节奏、登场、聚焦、爆点、回声、颁奖、个人感、可保存。

## 3. 保留与重构边界

### 必须保留

- summary v4 JSON、后端统计逻辑、缓存格式和接口。
- 现有 23 页注册顺序和按数据可用性控制页面显示的规则。
- `StoryPlayer` 的当前页与相邻页挂载策略、滚动吸附、键盘/触控导航和音频生命周期。
- 时间页到总览页的 `AnnualPeriodOverviewScene` 3D 封面通道及可定格转场。
- 服务端 PNG 海报生成、下载和分享管理链路。
- 已有曲绘、玩家形象、太鼓、封面流、烟花、音符轨道等资产能力。

### 必须重构

- 通用页面从“页头 + 内容卡片”转为全屏场景分层。
- 页面构图从多块同权信息转为唯一主视觉。
- 动画从通用淡入/上浮转为与太鼓、封面、数字和称号相关的语义演出。
- 文案从统计说明转为“情绪铺垫 -> 数据揭示 -> 记忆点收束”。
- 卡片只能作为少量辅助信息，不得承担整页构图。

## 4. Scene-based 核心原则

### 4.1 一页一个主角

每页只能有一个最高视觉优先级对象。标题、辅助数据和文案必须围绕它排布，不能与它争夺尺寸、对比度或运动强度。

第一轮五页的唯一主角：

| 页面 | 唯一主视觉 |
| --- | --- |
| Opening | 中央太鼓与封面舞台 |
| Profile | 玩家形象/装扮 |
| Overview | 总游玩次数 |
| Favorite Song | 歌曲曲绘 |
| Final Title | 年度称号 |

### 4.2 六层场景结构

所有目标页使用同一语义层级，而不是同一套版式：

1. `BackgroundLayer`：场景基底、封面取色、昼夜或颁奖环境。
2. `AtmosphereLayer`：粒子、烟花、光尘、节奏纹理等非交互氛围。
3. `MainObjectLayer`：本页唯一主角。
4. `DataFocusLayer`：与主角直接关联的核心数字或证据。
5. `CopyLayer`：标题、短句和收束文案。
6. `TransitionLayer`：连接前后场景的波纹、封面聚合、光幕或遮罩。

层级表达语义，不要求每页都有可见内容。空层不应生成占位容器。

### 4.3 数据是剧情爆点

- 核心数字先蓄势，再 count-up，到位时只反馈一次。
- 辅助数据最多承担证据角色，尺寸和动效强度必须低一级。
- `0`、`null`、`undefined`、`NaN` 或不可用字段不直接呈现，也不保留空槽。
- 数据不足时保持单主视觉结构，用一句自然收束文案结束。

### 4.4 页面间有继承关系

转场应复用上一页的主对象或运动方向。例如鼓面扩散进入玩家登场、封面通道旋转聚合为总览、曲绘余色留在歌曲页背景、金色光束收束成年终称号。页面不是 23 张彼此独立的幻灯片。

### 4.5 动效有节拍和因果

默认叙事顺序为：背景建立 -> 标题提示 -> 主视觉登场 -> 数据揭示 -> 文案收束 -> 低强度呼吸。淡入和位移只作为过渡手段，不能成为主要创意。

## 5. 场景模板

- `Hero Scene`：开场、玩家登场等身份型页面。
- `Impact Number Scene`：以单个大数字为高潮的总览页。
- `Song Memory Scene`：以曲绘、主色和歌曲信息构成记忆场景。
- `Pattern Scene`：将时间、速度、雷达、日历等行为模式转成一个仪表主视觉。
- `Award Scene`：以称号、勋章或里程碑完成仪式性收束。

具体规则见 `annual-summary-scenes.md`。

## 6. 构图与信息规则

- 以移动端竖屏为第一画布，优先适配 `390x844` 和 `720x1568`，同时保证 `844x390` 矮横屏可完成浏览。
- 使用 `100dvh`/`100svh`、safe area 和稳定的主对象尺寸，地址栏变化不能挤压或遮挡 CTA。
- 主视觉进入首屏，不通过滚动才能看见；场景内部禁止横向滚动。
- 标题控制在 1 至 2 行，辅助文案以一句为主，最多两句。
- 中日文长歌名允许换行和分档缩小，使用 grapheme 长度判断与 `overflow-wrap:anywhere` 兜底。
- 页面序号和全局导航属于播放器 chrome，不占据页面主视觉层级。

## 7. 视觉语言

- 色彩随场景变化：祭典深蓝与彩色灯光、玩家登场的聚光舞台、总览的明亮冲击、曲绘主色、颁奖深色与金色。
- 不允许 23 页统一使用浅蓝渐变，也不允许每页仅通过更换渐变色假装不同场景。
- 圆形来源于鼓面、波纹、节拍轨迹和聚光灯；矩形仅用于真实图片边界、操作控件或少量辅助证据。
- 显示字体沿用 `TaikoDisplay` 拉丁字形加系统中日文字体回退，不在本阶段新增网络字体。
- 图标使用项目现有图标库或明确符号；交互按钮必须有可访问名称和至少 44px 触控区域。

## 8. 文案结构

每页文案按以下职责拆分：

- 情绪铺垫：短、留白，为主视觉登场让位。
- 数据揭示：只解释用户需要理解的单位，不重复描述统计口径。
- 记忆点收束：一句能独立成立的回忆或判断。

标签使用“游玩记录 / 鼓点记录 / 谱面记录”等明确名词。避免“留下的挑战”等语义含混表达，避免实现说明和口径说明进入演出正文。

## 9. 性能与可访问性底线

- 继续只挂载当前页和前后相邻页；非活动页保持 `inert`、`aria-hidden`。
- `active=false` 时暂停 CSS animation、GSAP timeline、数字更新、封面时钟和粒子。
- 页面卸载、路由离开和 summary 切换时清理 timeline、RAF、timer 和监听器。
- `prefers-reduced-motion` 或 `saveData` 下直接显示终态，关闭循环、粒子和复杂转场。
- 背景动效不得影响文本对比度，信息不能只通过颜色或运动表达。
- 动态数字保留可读的最终 `aria-label`；字符拆分必须按 grapheme，不能拆坏中日文、emoji 或组合字符。

## 10. 第一轮范围与验收

第一轮只允许改造 Opening、Profile、Overview、Favorite Song、Final Title 五页及其直接依赖的场景/motion primitives。其余页面暂时保持功能，仅为后续迁移提供兼容壳。

验收条件：

- 五页不再以卡片或信息面板为主体。
- 五页分别只有一个主视觉焦点。
- 五页有完整且可清理的语义 timeline。
- 原有数据、页序、音频和 period-to-overview 转场契约不变。
- 三种视口、中日文、长文本、缺失数据、reduced motion 和 saveData 均可用。
- 根据 `annual-summary-anti-patterns.md` 自查后，不再呈现 dashboard 观感。
