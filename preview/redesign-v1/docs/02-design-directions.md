# 02 · 三个设计方向

可视版本在原型的 `#/review/directions`。A 嵌入的是真实原型，B、C 是概念稿。

三个方向不是三套配色。它们对「Viewer 首先是什么」给出了三种回答，导航、首页、内容密度和交互方式都随之不同。

| | A 譜面 Fumen | B 祭 Matsuri | C 帖 Chō |
|---|---|---|---|
| Viewer 是 | 一台查询与分析的仪器 | 一个热闹的玩家广场 | 一本私人的练习帖 |
| 首页是 | 个人驾驶舱 + 21 天练习谱面 | 大格子摊位 + 动态流 | 今天这一页日记 |
| 第一入口 | 全局搜索 | 社区动态 | 日期脊线 |

## A · 譜面 Fumen（推荐）

**理念**：玩家数据用谱面自己的语言来画。朱色是咚，浅葱是咔，山吹是连打；时间是一条从左到右的谱面带，判定圈落在今天。

- **气质**：精确、安静，有游戏的骨架但不卖萌。
- **色彩**：藍墨 `#17203a` 作文字与深色带；朱 `#e8482e`（主操作 / 刷新成绩）；浅葱 `#1fa5ba`（链接 / 信息 / 焦点）；山吹 `#f2b51d`（高光）；冷白纸 `#f3f5f8`。深色主题是夜藍 `#101728`，不是纯黑。
- **字体**：汉字用思源黑体（Noto Sans SC / JP），靠 400 / 700 / 900 三档字重做层级；所有数字用 Barlow Condensed 等宽数字 —— 七位数成绩在窄列里也放得下。
- **导航与信息架构**：桌面左侧 84px 窄轨，六个目的地（今日 / 曲库 / 成绩 / 成长 / 社区 / 工具）；二级页签并入顶栏；全局搜索（Ctrl K）常驻顶栏中部；同步状态常驻顶栏。手机底栏五格，正中是「咚」搜索键。
- **布局与密度**：高密度。表格、点灯表、分面筛选为主，面板是平面加细线，阴影只给浮层。
- **桌面**：主栏 + 吸顶侧栏（我的成绩、检视面板、当前目标），宽屏不留大白边。
- **手机**：表格换成列表行，对话框换成底部抽屉；歌曲详情把「我的成绩」提到最前，底部固定「游玩练习 / 想练这首」。
- **关键界面**：今日页的 Rating 鼓面刻度盘 + 六维雷达 + 当前目标 + 21 天谱面；歌曲详情的难度切换条 + 谱面图 + 右侧我的成绩；点灯进度表。
- **适合的理由**：查歌、看定数、对成绩是最高频的事，这个方向为它们各省了一到两步；音符三色本身就是数据编码，不需要另造图例；视觉语言来自谱面而不是官方角色，辨识度不依赖别人的 IP。
- **缺点**：第一眼不如 B 热闹，新玩家可能觉得「专业」；签名元素只有一个，必须克制，否则会沦为装饰。

## B · 祭 Matsuri

**理念**：Viewer 是一个庙会。首页是大家正在发生的事，功能是一排色彩鲜明的摊位，成绩像贴纸一样贴出来。

- **气质**：热闹、直接、亲切，像机厅门口的海报。
- **色彩**：朱赤 `#e63b2e`、山吹 `#ffc400`、群青 `#1f3fbf`、生成 `#fff6e0`、墨 `#1a1a1a`。
- **字体**：超粗黑体标题，3px 墨线描边，硬投影。
- **导航**：顶部一排大号胶囊；首页是「大格子 + 动态流」；社区排在第二位。
- **密度**：低到中，一屏 4–6 个大块，数据被做成卡片和徽章。
- **桌面 / 手机**：桌面居中 1200 栏，两侧色块；手机是它最自然的形态（2×2 大格子 + 粗底栏）。
- **适合的理由**：社区和晒分的氛围最好，新玩家上手门槛最低，识别度极高。
- **缺点**：和游戏官方的视觉太近，容易被当成官方页面；800 多条成绩的表格、六维对比在这套语言里排不清楚；高饱和大色块久看疲劳，深色模式很难成立。

## C · 帖 Chō

**理念**：Viewer 是一本练习帖。每天一页，写着今天打了什么；王冠和评价是盖在页上的朱印，成长档案就是把帖子翻回去看。

- **气质**：沉静、私人，有纸和印泥的质感。
- **色彩**：和纸白 `#fbfaf7`、墨 `#1c1b1a`、朱印 `#c8372d`、藍鼠 `#6b7b8c`。
- **字体**：宋体 / 明朝体标题，竖排日期与章节名，正文黑体。
- **导航**：只有四项（今日帖 / 曲目 / 帖簿 / 寄合），内容沿一条竖直的日期脊线展开。
- **密度**：中。单栏叙事，数字作为页边批注。
- **桌面 / 手机**：桌面是窄正文 + 宽页边；手机天然单栏，接近日记应用。
- **适合的理由**：和现有成长模块温和、不评判的文案语气最契合；「朱印」是很好的达成反馈。
- **缺点**：查一首歌的定数要先穿过叙事，高频查询变慢；竖排和宋体对中日双语、长曲名、表格都不友好；社区、工具、开发者页面很难放进「帖子」这个隐喻。

## 比较

| 维度（5 分制） | A | B | C |
|---|---|---|---|
| 高频查询效率 | 5 | 3 | 2 |
| 数据密度与可读性 | 5 | 2 | 3 |
| 成长叙事 | 4 | 2 | 5 |
| 社区氛围 | 3 | 5 | 3 |
| 辨识度 | 4 | 5 | 4 |
| 与官方视觉的距离 | 4 | 1 | 5 |
| 中日双语与长文本 | 5 | 3 | 3 |
| 实现成本（分高 = 省） | 4 | 3 | 2 |

## 结论：选 A，并从另外两个方向各拿一样东西

Viewer 的日常是「查一首歌」「看一眼成绩」「同步之后看看有什么变化」。这三件事都是数据问题，而且常常发生在机厅里、手机上、两首歌之间。A 是唯一把这三件事都缩到一步的方向。

- **从 B 拿：击打的手感。** 手机底栏正中的「咚」键、达成新王冠时的一次回弹动效（`--ease-hit`）。只在「确认」和「达成」两个时刻出现。
- **从 C 拿：叙事的语气。** 每周回顾的一句主题、成长档案里的「精彩时刻」、不评判的状态文案，沿用现有成长模块的口吻。
- **不拿的**：B 的高饱和大色块与描边贴纸；C 的竖排与宋体。
