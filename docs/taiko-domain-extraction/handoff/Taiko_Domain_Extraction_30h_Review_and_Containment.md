# Taiko Domain Extraction：近 30 小时执行审阅与收口指令

## 结论

**有实质成果，但执行目标与用户原始目标不完全一致，Phase 6 已膨胀为一轮独立的平台重构。建议现在停止继续扩展当前 Goal，安全保存成果，先完成一次有限的候选收口，不要继续自动补出下一个子步骤，更不要仓促统一部署。**

这不是判定全部工作失败，也不是建议撤销全部改动。Phase 3 和 Phase 5 已有生产切换记录，后续 Phase 6 则主要是未激活准备代码，必须分别处理。

## 三、明确的问题

### F01：原始目标被缩成了“纯算法抽离”

用户要求的是：**太鼓模块独立，Sakura_bot 仓库最终不再包含太鼓内容，不再维护两套太鼓模块。**

而 Phase 3 明确保留了 command、permission、消息、图片、HTTP、鉴权、文件、缓存；Phase 6 §6.1 进一步决定将新 publication 实现放在 Sakura 的中心 Infrastructure 包。

最新证据仍列出 Sakura 中的：

- `taiko/plugins/taiko.py`
- `taiko/plugins/utils/daily_ability.py`
- `taiko/plugins/utils/userdata_storage.py`
- `taiko/taiko_store/publication.py`
- `taiko/taiko_store/daily.py`
- `taiko/scripts/backfill_daily_ability.py`

**这能减少公式重复，但没有实现整个太鼓应用域脱离 Sakura_bot。甚至新增了由 Sakura 承载的太鼓基础设施。**

因此现有 Gate 3 PASS 应解释为“已定义范围内的纯内核委托通过”，不能解释成“用户要求的 Sakura 去太鼓化完成”。

证据：E03、E06、E12。

### F02：Phase 6 缺少有限的退出清单

原方案的 Phase 6 仅列 Writer ownership、P1a、Read Model、Database，未给出必须交付的边界、可延期事项、最大验证范围和工作量上限。

执行中已经扩展到：

- 自研不可变文件 publication、journal、recovery；
- 手动账号创建、认领、删除、恢复和持久回执；
- Goal 与绑定事务锁序；
- Developer Source/principal/scope 授权；
- Token 签发、撤销、quota；
- Hiroba 凭据发现与同步；
- 原生/分布式 Bot 的 QQ 验证码迁移；
- u0、daily、backfill、私有缓存；
- 仍未完成的 Read Model、百万记录成本和最终激活。

这些不是全无必要；问题在于把它们全部放在同一个自动持续的 Goal 中，而且“其余 Reader/所有 Writer/运维/成本/发布”反复作为开放尾项出现。

**不能按 Phase 0–5 PASS、Phase 6 IN_PROGRESS 推断快完成了。Phase 6 余下仍有独立的大型工作包。**

证据：E01、E06、E07、E08、E09。

### F03：关键规模验证又被排到了大量接入之后

Phase 6 选择加强版 JSON 后，先用小样本协议测试，再逐一改造各类 Writer、Reader、授权与事务；完整百万记录冷暖 IO/RSS、接管成本和 Read Model 仍在剩余工作中。

局部测试能说明一些正确性边界，但不能证明架构满足大规模成本。此前已经出现全量登记/回放性能问题，在这种背景下，继续把接入范围扩大后才做关键规模验证，存在再次返工的风险。

需要优先补一个小而真实的端到端规模探针：同一冻结候选、批准的合成输入、原资源 guard，分别记录登记、追加、Reader lease、请求进程数、锁等待与读取成本。没有批准的指标必须标为待决，不能把离线重建偷偷换成“缓存命中通过”。

证据：E06 §后续验收、E09、E12 limitations/remaining。

### F04：跨仓库候选处于“部分发布、部分准备”状态

材料最后记录：

| 对象 | 包内状态 |
|---|---|
| Sakura 源码 | 9.81.28 / `cc66b22`，已推送远端 main |
| 中心运行目录 R | Phase 6 新源码未同步/未重启激活 |
| Viewer | live 0.81.11；0.82.0 本地准备，等待统一发布 |
| taiko-bot | 0.2.7 已推送；本机业务进程未启动 |
| Core | 中心 0.1.1、客户端 0.1.2，按兼容需求分别固定 |

这不证明正在运行的服务已经出错，但要求立刻给出兼容性/发布矩阵。部分新客户端能力需要尚未上线的 Viewer 0.82.0 与显式 grant，不能把“各仓库已 push”当成“组合可运行”。

尤其不能在不知道 remote main 是否被外部部署者自动拉取的情况下，把未联合验收的版本当成正常可升级版本。

证据：E01、E04、E09、E10、E12。

### F05：分布式安装增加了原先未解决的依赖门槛

Phase 4 明确记载：Core 和 Contract 的私有 Git 安装需要 SSH 读取授权，没有权限时由维护者另提供固定 wheel。

这意味着原本面向持 Developer Token 部署者的 taiko-bot，增加了独立于 API 授权的代码分发依赖。Developer Token 不等于私有 Git 权限。

这不是要求将私有源码公开，而是要求真正验收：**一个只有被承诺的安装权限与 Developer Token 的部署者，能否在干净环境里装好并启动客户端。** 私有/公开包、wheel、许可证和版本 pin 都应有明确分发合同。

证据：E04 第 28–34 行。

### F06：共同 Core 不等于两端功能、策略完全一致

材料明确保留 center/client v2、target、可见范围、解析结构等 profile 差异；中心和客户端也分别固定 Core 0.1.1/0.1.2。

迁移时保留旧行为是合理的，不应为了统一而偷偷改公式。但这只能证明“既有差异被显式托管”，不能证明“两个 Bot 的太鼓功能已几乎一致”。

应将差异分为：权限/部署方式的必要差异、历史兼容差异、待消除的漂移。每项有决定，不能让 profiles 永久成为第二套维护分支。

证据：E02、E03、E04。

## 四、需要代码或完整集成验证才能定论的风险

以下是下一步必须回答的问题，不是本次已证实的生产故障：

1. **锁生命周期是否过长。** 报告中的部分 worker 在 Source EX/SQL 授权事务内完成上游同步或渲染，Hiroba 执行上限达 900 秒。要测同账号查询、撤权和更新的等待/超时，不可只凭顺序测试或小规模 5 秒竞争测试判断线上可用性。
2. **完整进程成本未汇总。** 一个 Growth compute 不等于一个 Python 进程；新增 `taiko_store.bridge` 的生命周期、与计算子进程的关系、并发时数量必须计入成本账本。
3. **真实 schema parity 未闭合。** 多处报告明确隔离 SQL schema 不含 production FK、仅做局部 TypeScript/实际函数测试。局部 PASS 不能替代候选组合的完整 schema/安装/启动/HTTP 验证。
4. **兼容文件与 canonical 对象的切换风险。** 协议要求激活前停止旧 Writer，不能让旧直接覆盖路径和新 publication 混跑。检测对象损坏不等于保证旧 Writer 不会破坏它。
5. **完整发布证据尚缺。** Phase 6 报告没有宣称真实上游、完整 NoneBot、全部 PNG、联合线上授权与百万成本已过。必须保持这个诚实边界。

证据：E07–E10、E12。

## 五、为什么不能把 30 小时都归为“模型空转”

Phase 0–5 有实际 package、consumer 委托、测试与部署；Phase 6 有新增实现和故障用例，不是只换措辞。

材料也记录了资源等待：2026-10-11 02:56 的 blocked 复核到 08:35 的恢复准入，间隔约 5 小时 38 分。它只能证明这两次记录之间的间隔，不能据此断言模型期间一直空等。

部分广泛回归耗时约 8–12 分钟，且记录了测试 harness、AST 装载、模块环境、fixture 等失败后的重跑。有优化空间，但没有完整逐轮日志，不能给出“浪费了多少小时”的可靠比例。

重点不是减少必要的崩溃/权限测试，而是避免每解决一个前置条件就扩成另一个完整子系统；未改变代码的回归证据可以按正确依赖范围复用，不能仅按被测文件自身 hash 忽略它改变过的依赖。

## 六、此前 v2 方案的问题

我之前的方案应承担明确责任：

- 用户要求整个太鼓模块离开 Sakura_bot，文档却保留 `taiko_adapter`、command、permission、message formatting，没有完成“纯算法抽离”与“整个应用域迁出”的区分；
- Phase 6 把四个大型工程名词作为一阶段，没有有限 backlog、非目标和停止边界；
- “保留旧实现可回滚”没有写明停止双重维护及删除的准入时点；
- 没有把普通分布式用户的包安装能力、跨仓库发布组合、最终仓库归属作为硬 Gate。

因此不能把这次问题全归咎于 Codex。它在相当程度上认真执行了一个范围过宽、终点与原始意图不一致的文档。

## 七、当前应当如何处理

### 立即动作：停止扩展，不销毁成果

在当前受控操作结束的安全点暂停 Goal；若正处于有界测试/子进程任务，让它经原 runner 正常完成或按其取消流程清理。不得粗暴杀其他服务、删除临时目录或清理未知文件。

保持已发布 Phase 3/5 不变。不要 blanket reset/revert，不合并新的未联合验收部署，不重新启动新的 Read Model、数据库迁移或用户流程重设计。

只做一次候选收口，输出以下三个产物：

1. `candidate-state.json`：每仓库源码 HEAD、远端、运行目录、安装 pin、已部署/未部署、schema 是否实际 applied；仅版本/hash/路径，不输出凭据。
2. `remaining-scope.md`：有限文件/模块清单，标出必须完成、暂停保留、延期；每项有可测试的退出条件，不允许“其余所有…”开放尾项。
3. `goal-gap-and-release-matrix.md`：用户要求的独立目标 vs 实际归属；客户端与后端/token/schema/package 组合兼容性；关键规模与完整集成尚缺证据。

这不是再做一轮全仓审计。复用已经生成的 inventory、hash 与报告，只补本轮改动的差量和缺失的整体视图。

### 重新定义后续 Goal 的终点

将“把 Phase 0–6 全做完”改为可直接验证的结果：

> 太鼓专用实现与运行资产由独立 Taiko 仓库拥有。Sakura_bot 当前工作树不再拥有太鼓专用源码、命令实现、渲染、采集/存储实现及维护脚本；历史 Git 记录不要求删除。两个 Bot 复用唯一实现，合法部署模式和授权差异显式配置。Viewer 通过明确端口消费，不依赖 Sakura_bot 的源码布局。

已有 Core/Contract 不需要推倒。若仍要让同一个聊天 Bot 提供太鼓命令，可采用独立 Taiko 包/插件或进程，但 Taiko 专用适配实现也须在 Taiko 仓库；Sakura 当前仓库仅可拥有真正通用的宿主加载能力。确需任何残余引用，必须由用户明确接受例外，而不是自行将目标改写成“只移公式”。

不通过关键词清扫误删其他领域的 `score`、`song`、`rank`。最终依据迁出清单、反向 import、资产/脚本/包依赖与可启动验证判定。

### 后续验证顺序

先冻结候选和发布组合，再做一次关键规模/锁等待探针；确认当前存储设计是否有希望满足批准预算。在此之前不继续铺满更多调用入口。必要的安全修复不能直接丢弃，能独立交付的以依赖清单拆出，不能独立交付的保留候选并标清原因。

后续正式迁出任务必须包含真正删除旧归属的提交和在非 Sakura 路径下的安装/启动/功能验证，不能只以 `old == new` 数值测试作为完成。

## 最终判断

**前五阶段有价值；Phase 6 的平台重构有必要成分，但范围和顺序需要纠偏。最重要的缺口不是“又少几个测试”，而是当前退出条件没有保证用户真正想要的独立归属。**

不建议继续让同一个无限尾项 Goal 自动跑下去；也不建议丢弃这轮成果或立刻大合并。先形成可审阅、可复用、可回退的候选，再按正确终点完成迁出。
