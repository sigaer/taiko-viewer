# 现有体验审计

## 结论与产品目标对照

Viewer 的功能基础已经超过概念验证阶段，但页面组织与视觉一致性仍有 beta 感。主因是不同阶段的页面分别采用落地页、工具表单、成长叙事和后台面板的组织方式，玩家需要自己把它们连接起来。当前已有的成长叙事、目标状态隔离、推荐到歌曲再到目标的流程应保留。

| 1.0 目标 | 当前可见表现 | 设计处理 |
| --- | --- | --- |
| 个人太鼓主页 | `/` 已有四态和成长面，`/my` 仍是欢迎语加链接网格 | 复用已有个人成长组件，明确首页和个人中心各自职责 |
| 歌曲与谱面成为任务上下文 | 曲绘、分析、试听并列；谱面图片和练习入口重复列出各难度 | 一个难度上下文，先谱面操作，再按需要展开分析 |
| 推荐→目标→反馈 | 已有推荐列表、推荐 token、目标确认和严格完成判断 | 保留完整列表与确认；加强当前位置和下一步的可见性 |
| 成长事实可信 | 已有观察、事实、冻结测量与记录范围 | 保留时序和覆盖说明，改善层级，不改变事实判定 |
| 年度总结和社区相连 | 年报已有沉浸故事、分享；社区可见年度分享帖 | 保留专属美术，统一外围导航和回到具体上下文的入口 |
| 开发者能找到正确接口 | 主导航文档链接为旧 token 指南；新指南在账号开发者页内 | 区分“用户授权说明”和“Developer API 指南”的信息角色 |

历史依据：[1.0 实施主控文档](../Viewer%201.0.0%20—%20My%20Taiko,%20in%20one%20place.实施主控文档.md)第 8 节、[1.0 产品合同](../release-readiness-1.0/01-feature-contract.md)。这些旧文件中的历史 Gate 状态不用于重判当前发布状态。

## 与 Moesekai 的信息架构比较

Moesekai 按数据库、活动、剧情、游戏、工具、个人等内容领域组织导航。首页优先给出当前内容，再提供捷径；音乐图鉴沿用同一导航和图形语言。Viewer 可借鉴的是领域命名、当前内容与查询入口的关系，以及相邻页面间的连续性。

| 比较点 | 可借鉴 | Viewer 的选择 |
| --- | --- | --- |
| 导航 | 内容领域清楚，当前位置稳定 | 用“曲库与谱面 / 练习与成长 / 社区 / 我的太鼓”组织，不复制庞大菜单 |
| 密度 | 图鉴紧凑，易扫描多首歌 | 详情页保留大曲绘识别能力；推荐使用行式列表，避免一味缩小卡片 |
| 首页 | 用真实内容代替长篇介绍 | 访客先搜歌；已登录先接续当前目标与变化 |
| 视觉连续性 | 标题、控件、表面风格贯穿 | 建立统一 token 和组件语义，保留年报特例 |
| 首次访问 | 有个性化引导 | 不增加阻挡主任务的强制引导；在需要绑定、同步时就地说明 |

本轮比较来源为[实际首页](https://pjsk.moe/zh-cn/)与[音乐图鉴](https://pjsk.moe/zh-cn/music/)，以及上一轮同日浏览器参考截图；没有把参考站的全部功能或性能视为已验证。

## 全局根因

分类：IA 信息架构；V 视觉；C 文案；I 交互反馈；M 移动端与无障碍。优先级是后续设计实施顺序，不是发布阻断等级。

| ID | 分类／优先级 | 根因与影响范围 | 证据 | 统一处理 |
| --- | --- | --- | --- | --- |
| G01 | IA／先做 | `/my`、工具、首页成长面分别组织同一组个人能力，Training 与 Progress 缺少共同导航 | live-my、fixture-home-ready、fixture-recommend-list、fixture-passport-ready | 一个导航家族，保留现有路由、账号和难度上下文 |
| G02 | V／先做 | 米棕色定制首页、蓝色 Element 控件、白色方形卡片并存；按钮、圆角、阴影缺少一致层级 | live-home、live-scores、fixture-b30-form、fixture-profile-ready | 全站共享颜色／字体／间距／组件 token，不逐页自行选色 |
| G03 | C、V／先做 | 页头默认输出描述，内容卡片再次输出标题和说明，搜索与结果被下推 | live-songs、live-api-guide、fixture-scores-ready | 每页一个主标题；说明按任务必要性出现；SEO 描述与可见描述独立 |
| G04 | C／先做 | `userdata`、本地文件、bot 指令、拉取／分发等实现词进入普通玩家流程 | fixture-scores-ready、fixture-b30-form、live-api-guide | 普通页面只表达行为与结果；技术细节集中到真正的开发者文档 |
| G05 | M、V／随后 | 同一内容在桌面大容器与手机单列间简单缩放；曲绘、介绍、表单占用手机首屏 | live-song-390、fixture-recommend-list-390、fixture-scores-ready-390 | 依据任务重排与折叠，保留内容和操作，不只是减字号 |
| G06 | C、M／先做 | 中日文元信息与页面内部翻译不同步，日语页面保留中文标题／面包屑 | live-ja-api-guide-390，`pages/docs/score-token.vue` | 元信息、导航、状态和内容均走同一 locale；CJK 真实长文本验收 |
| G07 | I、M／随后 | 受限入口、数据加载、生成图片和一般读取失败采用各自表达；恢复入口缺少统一位置 | live-annual、live-passport、fixture-progress-form、fixture-profile-ready | 共享状态模式；保留有效内容，错误就地恢复；不把合法拒绝写成系统故障 |
| G08 | V、M／随后 | 标题、次级文字、数据与交互边界未形成统一的可读与可点标准 | live-song、live-songs、fixture-developer-guide | 16px 正文、可读辅助字、44px 触控区、明确焦点；颜色测试与真机验收分别进行 |

G08 的全站对比度、屏幕阅读器与全部触控命中区仍需实现后逐组件验证；本审计不把疑似问题写成 WCAG 不符合结论。

## 保留项与待实施验证

保留手机底部导航、搜索、完整推荐列表、推荐上下文 token、目标确认、目标归属隔离、成长事实去重、冻结测量、周报范围提示、年度报告原有故事和社区分享。没有证据支持把它们统一删掉或替换。

尚未实测：真实账号登录后的所有生产数据组合，Safari 的音频／全屏／安全区，屏幕阅读器完整流程，全部浏览器的长表格和失效授权状态。将这些纳入对应页面迁移后的回归清单，不用本轮静态原型冒充通过。
