# Viewer Development Principles

本规范适用于所有后续 Viewer 开发者和 Agent。已验收的架构和契约是事实基线；批次授权不等于生产迁移或发布授权。

## 1. Avoid Repeated Audits — 减少重复审计

只检查本次修改直接涉及的代码和依赖。不因新批次重新审计整个仓库，不重复已完成的消费者迁移、来源审计和测试。发现新的真实矛盾时才扩大范围。

## 2. Targeted Testing First — 定向测试优先

每个工作包先运行相关定向测试。文档修改不触发完整构建；独立模块不重复无关 Core、Golden、全仓测试。阶段集成执行一次必要的跨模块验证，完整回归主要用于正式发布验收。禁止删除测试或降低断言来通过验证。所有 QA 遵循既有内存隔离规则，禁止与构建争抢资源。

## 3. Feature Delivery First — 优先实际功能

新增能力必须说明最终用户如何使用。不要无限扩大文档、测试和基础设施治理，不为完美架构延迟具备条件的产品功能。文档只维护真实契约、重要决策、操作和验收结果，不重复创建相同报告。

## 4. Strict Data Protection — 严格保护真实数据

任何生产数据库变更须用户单独明确授权。真实成绩、Goal、Measurement 的读取与写入均遵循授权边界。禁止复制生产玩家数据到测试库；数据库变更先在隔离环境验证。禁止自动修复、回填、重写来源不明数据。保留原始 Baseline、完成证据和历史身份。普通候选开发不包含生产迁移、发布和部署。

数据库测试必须验证实际 `SELECT DATABASE()` 结果以 `_test` 结尾，并要求明确测试写入授权 `TAIKO_ALLOW_TEST_DB_MUTATION=1`；环境变量名称不能代替实际数据库身份检查。

## 5. Parallel Development — 独立工作包并行

优先使用 Codex 原生 Subagents，每个写代理使用独立 worktree，明确文件所有权，禁止同时修改同一文件。公共 Schema、接口和迁移由 Lead 控制；子代理没有文件或终端工具时只能做设计审查。Lead 负责集成、冲突处理与验收，不得把设计意见称为代码执行结果。

## 6. Deliver Usable Product Experiences — 形成真实体验

核心功能批次尽可能形成 API、持久化和用户可见的最小闭环，不长期停留在离线纯函数。优先扩展已有 UI。用户状态反映真实数据；不得用静态示例或虚构数据冒充生产能力。能力不完整时明确限制，不显示虚假的成功状态。
