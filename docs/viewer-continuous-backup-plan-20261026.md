# 持续备份 RPO/RTO 最小生产变更方案

日期：2026-10-26，Asia/Shanghai。仅设计，不是执行授权。见 [唯一 Release Gate](viewer-1-release-gates-20261023.md)。本轮没有运行全量恢复、改调度/范围/正文、数据库权限或存储位置，latest-verified仍为10月17日旧点。

## 已有能力与缺口

沿用O1：RPO≤900s，核心RTO≤7200s；成功的一次检查点不能代替持续RPO。原当前规模35表/90,092文件/6.955GB的诊断捕获及原生还原证据保留。原生195.887s、验证40.261s、受控工作流300.649s均为已坏Source诊断包的耗时，不能当作有效恢复点或完整RTO签收。

现有加密路径、密钥分离、保留旧verified及原子指针机制可复用，但没有当前核心全量集合的持续调度。每日管理备份不覆盖全部35表/Publication。MySQL只读核对为log_bin=ON、MIXED、row_image=FULL、GTID=OFF、sync_binlog=1、InnoDB commit flush=1；现有主体具有replication能力，本轮未使用其抓取binlog。SQL日志不能证明文件Publication、历史测量与撤销同代；不能仅加binlog收集便声称核心PITR合格。

首先必须完成已授权的Source实际修复，再用现有机制取得首个健康实际规模同代点和完整隔离恢复。没有这个基线，下面持续方案不启动、verified不推进。旧坏revision及历史不可恢复边界须按Source修复申请明确裁决，不能隐去。

## 推荐的最小持续链

1. 同一现有私有存储和加密/保留机制，最多一个捕获任务、一个隔离验证器，默认每5分钟尝试一次；每次有截止时间、资源准入、容量上限、互斥和失败告警。不得叠加积压任务、放宽Worker/内存或删除最后健康verified。
2. 捕获闭包固定为已审查35表、身份/Session/Key/绑定、六张授权/审计表、Source生命周期、current/history/冻结daily/Growth/Goal、Publication vector与全部活动committed引用、所需配置/精确构件；新表或格式差异即阻断而不静默遗漏。
3. 背景预拷贝及流式加密在短fence之外。协调SQL快照与全体Source vector时，必须覆盖创建/删除及不在Publication对象内的daily/配置写入。仅逐个SH或拿两个时间点拼接不够。未变文件只能依据已验证父链及fence下相同inode/size/mtime/ctime证明复用；变化、删除、引用集及父链hash显式记录。候选点先写加密完成标记，不直接标成可恢复。
4. 基线完整恢复一次通过后，隔离验证器可复用**已验证恢复基线**应用显式增量闭包及该点同代SQL快照；检查35表原生值摘要/DDL、全部活动引用、Source读路径、原事实/身份、撤销与审计。不得把未经证明一致的旧文件作为新代数据。这个增量验证能力目前未实现/实测；若只能每点完整还原，则必须重新测预算，不能套用下方120s。
5. 全部必要校验通过后才原子推进verified；捕获成功但验证失败只保留候选/诊断。撤销连续性无replay证明时，恢复开放前使Session/Key/Grant/待确认凭据全部fail-closed，保留属主、绑定、Source、历史与审计；SQL binlog开启不自动改变此政策。

**不能直接每5分钟运行旧一次性脚本。** 旧脚本暂停五个服务，实际静止约20s；反复停止Viewer影响正常业务，且新调度、静止窗口、捕获范围都没有授权。推荐需要经过审查的短时一致快照协调能力，不停止Web服务；现有单Source锁不足以单独证明新建Source及所有文件的全局闭包。若不能取得该能力，只能申请明确维护窗口作一次检查点，不能称为持续合格机制。这不是重开已签收的Writer架构迁移，而是新增备份协调的单独受控变更。

## 时间与资源预算（设计上界，非实测）

设尝试间隔S=300s，fence/加密完成≤45s，隔离增量验证≤120s，提交/调度余量≤15s，D≤180s。正常最大verified年龄≤S+D=480s；一次错过尝试≤2S+D=780s，距离900s余120s；两次错过将超目标，必须告警并将持续RPO记为不合格。验证耗时不能以已知195.887s原生全量还原替代120s目标；D、抖动和故障情况下的实际年龄都须测量。

保留现有准入/互斥和资源上限，不因调度到期强行启动。构建可持维护锁30分钟、QA可15分钟，均能超过备份预算；**只加timer无法满足RPO**。需要截止时间感知的运行准入：将使备份错过预算的新QA/构建拒绝启动或安排批准窗口，不移动编辑器、不杀未知进程。若需中止已开始的owned任务或增加互斥例外，须独立授权，不能本轮默认。未能安排资源时明确RPO违约，不用旧指针/旧年龄掩盖。

建议告警：verified年龄≥600s预警，≥780s紧急处置，>900s明确FAIL；同时监测候选年龄、验证队列、磁盘/密钥/远端交付失败、OOM和锁等待。没有已批准通知渠道时先设计本地状态/日志，不擅自发邮件或消息。保留策略由容量预算裁决，旧verified不因新候选生成而删除。

## 需要的额外生产权限

- 安装并启用持续timer/service、只读捕获与私有验证worker，批准精确命令/身份、资源和时限；这是**新的调度授权**，不沿用一次性150s静止授权。
- 审批捕获程序及备份正文格式/增量父链，允许读取35表/相关私有文件/密钥并在**原路径**写加密候选及校验状态；允许必要短SQL/Source协调fence，并审批新增协调代码的标准发布。当前SELECT/LOCK能力沿用，不因此修改生产数据库权限。
- 在现有隔离根运行skip-networking的测试MySQL及受限HTTP验证，原身份/正文仅留私有范围；实际生产规模原生还原完成后，明确批准持续隔离数据保留、增量验证和清理策略。不得对生产执行验证业务写入。
- 批准verified原子指针的自动推进条件、维护准入规则和告警渠道。新存储、异地、PITR、额外replication用户/GRANT均**不在最小方案中**，如需要再单独申请；本轮无异地恢复能力声明。

## 完整 RTO 计时与签收

T0=故障实际造成核心服务不可用；T1=决策/隔离入口；T2=选择可验证点并取得加密物料与密钥；T3=DB+文件闭包还原；T4=全部活动committed引用/SQL摘要与历史事实校验；T5=撤销连续性验证或全部凭据fail-closed；T6=隔离合成主体验证认证、当前/历史读取和核心写入；T7=批准开放。完整RTO=T7−T0，必须≤7200s，下载/解密/还原/验证/授权处置和开放决策全部计入，失败尝试及人工等待也计入。

核心可写验证在真实规模恢复环境内使用独立合成主体，不写生产真实业务；入口/后台Writer在授权核对完成前关闭。若还要用户重新登录/验证或补授权，不能仅以mysqld启动即宣布RTO结束。RPO按T0时可用的最新**已验证**检查点cutoff计算；检查点后撤销若无法证明，必须记录恢复开放限制。

执行顺序：Source修复获批完成→首个健康当前规模同代捕获及完整RTO演练→审查并批准持续链及预算→连续至少24小时记录每点cutoff/完成/验证/指针时间、每时刻verified年龄和资源→一次捕获失败、验证失败、锁占用/资源拒绝/丢失密钥等受控演练→由现有发布决策流程签收。合成时间模型、一次检查点或旧诊断包都不能提前代替这些证据。
